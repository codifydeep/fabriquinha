# CTO repair admission and HTTP diagnostics

The model proposes `repair_scope.test_paths` and `repair_scope.cases` only.
The controller resolves the frozen-test receipt from the failed implementation's
native `tests` input, checking the unchanged source contract, parent handoff,
release and exact frozen tests in the incident snapshot. Legacy callers may
supply `tests` only when it matches that authoritative receipt. Descriptive text
or another receipt cannot grant repair authority. Old receipts remain unchanged.

The CTO receives this context for every eligible implementation incident, not
only diagnostics already carrying an explicit test-repair proposal. Admission
still requires a current experiment, an eligible settled incident and bounded
existing cases/files. It is not approval of a test change or delivery.

Two identical rejected diagnostic calls in one activity prevent the same handler
from running a third time. The agent must inspect the returned error/context,
change its unsupported proposal or record a justified hold. This does not create
an automatic approval, unlimited retry or new orchestration service.

The fixed read-only diagnostic wrapper observes HTTP responses >=400, recording
path, status, active test and the test that created the browser context. It does
not record cookies, headers, bodies or query strings, and never ignores browser
errors. Events remain bounded sandbox clues. They are supplied with the exact
job to the CTO; old logs lacking them remain historical. The pinned suite,
assertions, discovery and delivery verdict are unchanged.

Unexplained 404s must be traced before deciding between product correction,
fixture correction or infrastructure recovery. A tie test needs a reachable,
deterministic setup; an assertion on an impossible deal is not adequate coverage.
A deliberate negative API probe may use the same browser context's HTTP client
with its cookies. Message-only console exclusions are not a substitute for
identifying an expected request and preserving unexpected-error detection.

Installation is assisted maintenance: paused/drained services, verified cold
backup, source publication, exact failed CTO-card resume through the native
unblock transition. Native block recurrence history remains; Hermes deliberately
resets its consecutive spawn-failure counter during unblock. No product workspace,
frozen test, graph or old decision is edited. Independent repair review/freezing,
implementation review, CI, deployment and QA remain mandatory. A resumed CTO or
passing diagnostic does not constitute homologation or autonomy.
