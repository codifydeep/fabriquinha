# Evidence-bound technical remediation planning

An exhausted recovery chain must produce a new technical work contract, not
another identical retry, an unbounded recursive child, weakened tests, or a CEO
architecture question. Planning is separate from permission to execute.

## Implemented path

1. The controller recognizes an exact source-bound diagnostic experiment,
   completed independent CTO diagnosis and two preserved revision generations.
   It verifies complete source reads, immutable Red, unchanged acceptance from
   the hash-bound context capsule, and the original registered Git base.
2. It pauses only that original route. Failed tasks, snapshots, Red, full-suite
   failures, prior decisions and ancestry remain preserved. It registers one
   durable recovery-plan intent for the source.
3. A dedicated Multica issue contains the original acceptance criteria and
   fixed diagnostic facts. CTO gets read-only access to the failed snapshot and
   proposes three strictly dependent steps: NEW-test harness repair, product
   implementation after approved tests/Red, then controller publication/QA.
4. Every step must retain every acceptance ID. The controller rejects missing
   criteria, incorrect dependencies or edit scopes, mismatched hashes, stale
   task/wakeup identities, and incomplete source reads.
5. Tech Lead reviews the exact plan independently after full source inspection.
   A rejection remains a visible technical hold; it does not automatically
   repeat the same planning request or ask the CEO for a technical decision.
6. An approval records `plan_approved` only. It cannot change the original depth,
   authorize a worker, approve a delivery, invent Green, merge, deploy or mark
   the release homologated. The next gate is a separately validated executor
   adapter consuming that exact reviewed contract.

## Durability and isolation

`technical_remediation_plans` persists issue intent, dispatch, actual native
task/wakeup identities, proposal hash and independent review. Stable issue
titles and wakeup markers prevent duplicate remote work after a restart.
Uncertain API writes enter an observation phase using read-only lookup; missing
handles are not authority for another POST. Missing worker acceptance or a
progress deadline produces a technical hold instead of an endless wait.

Planning mounts only the controller-selected snapshot read-only. Workers have
no infrastructure credentials/socket, shell/write authority, or arbitrary
command input for this operation. The proxy requests a strict non-executing
schema; controller validation independently checks the returned decision.
Multica card metadata projects stage, owner and next action without controlling
execution or turning notification failures into successful work.

## Typed terminal transport

Plans and their independent reviews have a dedicated non-executing submission
function. The proxy requires an exact matching evidence binding and canonical
schema, preserves model-supplied arguments, and rejects extra authority or stale
hashes. Mandatory source reads still precede terminal submission. This transport
does not execute a worker tool or accept the plan on behalf of the controller.

`remediation_transport_probe.py` qualifies the adapter without provider calls:
plan/review values must survive unchanged, while execution grants and stale
evidence must fail. Offline qualification is not evidence of a successful live
agent round trip. Installing a changed adapter does not reset a failed planning
task: a separately qualified, bounded recovery transition must preserve its
failure and authorize any fresh dispatch. No such automatic retry is currently
enabled by the normal watchdog for blocked planning tasks. A controller-only
maintenance transition can qualify one changed-protocol dispatch from an exact
preserved plain-JSON rejection, closed execution and complete source reads.
It requires a canary on the installed proxy image without credentials, network,
socket or persistent mounts (the inherited `/opt/data` volume is replaced with
a fixed empty tmpfs). This transition retains its predecessor and is consumed
once; failure of the new typed attempt remains blocked, not retried indefinitely.

An independent plan review also has an opt-in, once-per-execution format repair
for a sole oversized `reason`. The model must submit new arguments under the
unchanged 600-character limit. The proxy preserves decision, evidence/plan
hashes and flags exactly; it neither truncates an answer nor accepts a plan.
Other invalid fields are ineligible. The durable call ledger fences retries and
every provider attempt counts against the same hard budget. A failed review
may receive one changed-protocol maintenance dispatch only after preserving its
rejection and qualifying the new isolated canary, without rerunning the CTO.

The first intake is qualified for the service-mode diagnostic fixture. This
does not claim generic remediation for every project or a complete autonomous
release. Generalization and the plan-to-execution adapter remain qualification
gates; all product PR/CI, deployment and same-SHA browser-QA requirements remain.
